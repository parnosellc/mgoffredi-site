The system at a glance

Example URL

movesmethod.com/tkp-fcvsl01a-1

Format

[product]p-[page-type][version-number][version-letter]-[variant]

Example decoded

  • tk — Toolkit (the product the page sells)
  • p — page (literal, separates the product from the page-type)
  • fcvsl — forced-consumption VSL (the page type)
  • 01a — version 01a
  • -1 — variant 1

Page types

CodeMeaning
fcvslForced-consumption VSL. Product is locked until the user watches through the video.

Why this matters

Right now our landers have ad-hoc names: /watch, /toolkit-7479, /move, /toolkit-a, /now943876. None of them tell you what the page does or what version it represents. You have to know the history of each lander to understand what it is.

Under this proposed system:

  • A URL is a self-describing identifier. Anyone reading the URL knows the product, the page architecture, and which version it is.
  • Variant testing has a clean structure — variant-1 vs variant-2 of the same page tells you they're A/B variants of the same underlying version.
  • New landers get clean slugs from the moment they're created, instead of inheriting whatever the developer felt like typing that day.

The workflow this enables

In the future, marketing names the funnel and engineering makes the URL be that slug. One-shot, no debate.

Practically: marketing says "we need a new fcvsl page, version 02a, third variant" → engineering deploys it at movesmethod.com/tkp-fcvsl02a-3. The URL is determined by the spec; no naming meetings, no committee.
